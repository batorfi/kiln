## Phase 2 — the harness (2026-10-26)

1. **The oracle's I1–I3 were sharpened while writing its test (T009).** The data model's wording made "a record with a waiting gate" both I1 and I3. The code now works from three facts — G (the gate's state), R (record count), D (decision task status): I1 and I2 are the two halves of "G ⇔ R", and **I3 is the disagreement between R and D** — the half-applied move. `data-model.md` §2 was updated to say so. I5 and the unblocked half of I6 are properties *across* restarts and live in `checkStability` (two inspections, no move between them).
2. **`GateState` gained `unknown`** (a gate that was never opened); `state()` on such a gate must not throw. Contract updated.
3. **The client distinguishes "refused" from "outcome unknown".** A request whose owner was killed resolves as `refused(store-error)` with detail `connection-lost` or `timeout` — never hangs. The caller cannot tell from that whether the move committed; it must ask `state` or retry the same key. This matters for the random-kill scenarios (T032): such a trial is judged by the store afterwards, not by the reply.
4. **Not-ready is observable.** The owner listens on its socket *before* its strategy has started; a request in that window gets `not-ready` (`OWNER_START_DELAY_MS` makes the window wide enough for a test). This is the "startup race" the plan names for C1.
5. **`recovery-start` is an owner-level kill point** (first thing after argument parsing, on every start). Control strategies do not declare it; native strategies will, because a restart is where their recovery runs.
6. **A harness bug found by mutation (not by review): a failing test leaked its owner process and the run hung.** Sabotaging the correct control so it never commits made `owner-client.test.ts` fail an assertion *before* its `killNow` — and the leaked owner kept `node --test` alive forever. Fix: `Store.cleanup()` now kills every process started on the store (test C5 proves it), and the `test` script has `--test-timeout=60000` as a backstop. Lesson for every later scenario: **cleanup must be unconditional, and a harness that hangs on failure is worse than one that fails.**
7. **Mutation checks, all caught** (committed before mutating): the kill hook exiting gracefully instead of `SIGKILL` (1 test fails); the oracle no longer detecting I3 (2 fail); no longer detecting I4 (2 fail); the control rolling back instead of committing (2 fail, in 1 s after the fix). The kill test K3 genuinely asserts `signal === "SIGKILL"` and that no `exit`/`beforeExit` handler ran.
8. **`node --test` and type stripping:** `.ts` files run unflagged on Node 25.9.0 and 22.19.0; `import.meta.main` is avoided in favour of a local copy of r12's realpath-based entry guard (`src/entry.ts`) — nothing is imported from `kiln/`.
9. **Socket path length:** the owner's socket lives at `<tmp>/r42-XXXXXX/o.sock` (~65 chars), inside macOS's ~100-character limit for Unix-domain socket paths.

## Phase 3 — the evidence machinery (2026-10-26)

1. **A violation outranks missing evidence.** `deriveStatus` returns `not-held` if any scenario ran and violated an invariant, *even beside scenarios that did not run*; only then `not-proven` for any gap; `held` only when every scenario ran and passed. Reason: an observed failure is a fact, an absence is only an absence — hiding a failure behind "not proven" would be the more favourable lie.
2. **Supporting evidence can condemn but never acquit.** Random-kill results carry `supporting: true`: a violation found by them counts against the guarantee, but they alone never make it `held` (a few hundred random kills prove nothing about absence).
3. **The runner fails by name, and it fails *before* it prints.** With no scenario registered, `npm run evidence` exits 1 `evidence-zero-tests` and prints no table (observed). An unbuilt strategy is skipped (and listed on stderr) in a default run, but asking for it explicitly with `--strategy` is a usage error (exit 2) — a named strategy that silently vanished would be a vacuous pass.
4. **A kill-point shortfall is reported, not hidden:** 2 of 3 declared points exercised ⇒ the run exits 0, the note names the missing point, and the guarantees those points test are `not-proven`. *No* declared point exercised, or none declared, fails `evidence-zero-kill-points`.
5. **`evidence-scenario-error` was added** to the contract's list: a scenario that throws something other than an owner failure is a harness bug; its guarantees are recorded `not-proven` and the run fails.
6. **The report checker got its own test file** (`tests/report-check.test.ts`, 8 cases) — not a task in `tasks.md`, added because a checker nobody has seen fail is the thing this spike exists to avoid. The final count of test files in the plan/tasks (13) becomes 14.
7. **Mutation checks, all caught** (committed first): a scenario that did not run no longer spoils `held` (1 test fails); random kills alone make a guarantee held (1); violations ignored (3); non-enforceable caveats ignored (1); test-only controls counted as candidates (1); zero scenarios no longer fails (2); a caret range no longer fails the install check (1).
8. **The report skeleton fails `report-check` on purpose** (11 failures: ten placeholders and the missing evidence). The failure is the reminder; it stops failing only when T061 writes the report and `npm run evidence` has produced `out/evidence.json`.

## Phase 4 — C1 `native-signal` (T038–T040, 2026-10-26)

1. **Built as described, first run worked.** Gate task (`spike.gate`: open → settle) owns a decision task (`spike.decision`: wait). The decision's phase registers a single-shot slot in an owner-level map and awaits it; a move makes it perform ONE `runtime.commit` that writes the `spike.move` document (a conversation-scoped *document family* keyed by gate id) and returns the task's own `terminal`. `submit` judges every duplicate against the **stored record**, never memory; the first caller takes the slot, the others await its commit and then get `repeat` / `refused(lost-race | key-conflict)`. 20 concurrent same-key submissions in one process: 1 `committed`, 19 `repeat`. API differences from the task text (no surprises beyond these): the Gate stores the decision id in its checkpoint (`{phase:"settle", decisionId}`) because `ownedTasks()` lists live tasks only; both tasks need an `abort` handler (required by `defineTask`) — they commit `aborted` and are never exercised; `open` creates the gate task itself (scan-then-create inside one root commit, so concurrent opens cannot double-create) instead of the gate creating itself.
2. **What "the gate is settled" means here (a choice, recorded).** `state()` and `inspect()` derive the gate from the **move record** (a record exists ⇒ settled), and judge the decision task separately (I2/I3: record ⇔ decision terminal with that key). The gate *task* is a projection that converges (decision terminal → gate wakes → settles). A kill at `gate-wake` leaves record + terminal decision + a gate task not yet advanced; on restart the scheduler advances it by itself. `start()` waits (≤ 5 s) until every live decision has re-registered and no gate task is ready/running, so `ready` means "converged". Had the gate been derived from the gate task, the lag at `gate-wake` would have been reported as I1 — a stricter reading, not tried.
3. **T040 result: `native-signal` — a, d, e `held`; all 10 declared kill points exercised (10 of 10) + 600 random kills; b, c `not-proven` (Phase 5).** Caveat declared and enforceable: d holds only with `settings.restartLimit = Infinity`.
4. **The restart limit is real and bites (negative proof, observed).** With `RESTART_LIMIT=5` (the library's default) and 7 consecutive kills with no move, the next owner reports the gate `waiting` but a valid move is refused `not-ready` — the decision task is parked and never re-registers; the `restart-limit` scenarios fail with I6 (`restarts` ≥ 5 on a live task). With `Infinity` the same move commits. `inspect` has no Harness, so it reads the limit the owner ran under from a sidecar file `restart-limit` next to the store; the *parking itself* (not just the counter) was confirmed through the refused move.
5. **A phase that awaits across a restart re-registers quickly, but not instantly.** Restart → `ready` took 178–197 ms (5 restarts; `ready` is withheld until the decision has re-registered). A move asked at `listening`, before the strategy has started, gets `refused(not-ready)` — the startup race is real, and handled by the contract (the caller retries the same key; the owner's `not-ready` is what r13's seam must expect).
6. **The changelog's caution holds, as a cost not a failure.** Waiting inside a phase works, but only because (a) `restartLimit` is `Infinity` and (b) the owner process keeps the slot in memory; the library has no durable "wait for an outside event" state, so the phase re-runs from its top after every restart. Recorded as a caveat for the report: *a wait inside a phase is invisible to the library's scheduler (`harness.inspect()` shows the decision as `running`), and nothing but the restart limit distinguishes it from a stuck task.*
