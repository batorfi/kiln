# Implementation notes: real local workers (row r16)

## T002 — inventory of call sites that change

- `durable/src/tasks/unit.ts`'s `work` phase: the `stepMs` stand-in (`await new Promise(...)` in a `setTimeout`) is what a real role's step replaces with a conversation turn. The surrounding checkpoint/commit/lane-acquire/release shape is unchanged (research R3).

## T004 — a real cycle in the plan's boundary edges, corrected

`research.md` R2 and `data-model.md` §9 both state the new boundary edges as `durable → workers` **and** `workers → lane, durable, contracts`. Implemented literally, this is an actual cycle: `durable → workers → lane → durable` (`lane → durable` already exists from r13) — `checks/boundaries.ts` itself detects exactly this and fails the rule file by name (`boundary-rules-invalid`, "the layers form a cycle"). This is not a style nit; the checker is correct to refuse it; a two-way package dependency has no real direction.

**Correction made** (the smallest change consistent with the codebase's own existing pattern): apply the *same inversion r13 already uses for `durable`/`lane`* to `durable`/`workers`.

- `durable`'s allowed imports are **unchanged** (`["contracts", "record"]`) — it never imports `#workers/*` directly, exactly as it never imports `#lane/*` directly today.
- `workers`'s allowed imports become `["contracts", "record", "lane"]` — **not** `durable`. `contracts/worker-conversation.md`'s pseudocode shows `TurnInput.unit: TaskId`, but `TaskId` is defined in `durable/src/types.ts` as a bare `type TaskId = number`; importing it would re-create the cycle. `workers/` uses a plain `number` for a step's id instead (a locally-named alias is fine; importing the type is not).
- `unit.ts`'s `work` phase (T019, out of this phase's scope) will call a `runTurn`-shaped function through **a port on `Services`**, the same way it already calls `s.lane!.acquire(...)` through the `LaneApi` port `durable` defines but never imports the concrete implementation of. The concrete `workers/src/conversation.ts`'s `runTurn` is wired in by whoever composes the factory — see the next finding, because today **nothing does**.

`checks/boundaries.json` as committed in this phase: `durable: [contracts, record]` (unchanged), `lane: [contracts, record, durable]` (unchanged), `workers: [contracts, record, lane]` (the only new edge). Verified acyclic and all 84 of `checks/tests/boundaries.test.ts` + `boundaries-dependencies.test.ts` pass unmodified against it, including B1 (the real package tree) and B3 (`lane → workers` still correctly forbidden).

**Not fixed in this phase** — out of scope for Setup/Foundational (T001–T014), which only needed the machinery to exist and be unit-tested in isolation, not wired into the real CLI process. Flagging here so whoever picks up T018 (`unit.ts`'s real call) or T036–T037 (the real walk) does not discover this mid-story. ## T013 — a significant, confirmed correction to the spec/plan: `lane.transition` cannot be emitted

**Finding, not a judgment call — stop-and-report, then fixed the implementable part.** `research.md` R9/R10, `data-model.md` §8 and `tasks.md`'s own ground rules all state `lane.transition` is "declared [in r15's catalog], never emitted" and that this row is "the row that would finally emit it" (FR-027). This is **wrong**, confirmed against the real catalog:

```
packages/contracts/src/events/catalog/lane.ts:
  legacyEntry("lane.transition", obj({ kind: ..., from: str, to: str, reason: str }, ["kind"])),
  // the first program's residency changes and costs: read-only, they exist so its streams can be replayed
```

`legacyEntry` sets `legacy: true` and `committable: false`. `packages/durable/src/record/append.ts` refuses it outright: `event-type-read-only — "lane.transition represents the first program's streams: it can be read and replayed, never committed"`. This is deliberate, existing, tested machinery (byte-identical replay of r1–r8's old streams depends on legacy types staying exclusively legacy) — not a bug to route around. Confirmed by running the actual tests: every attempt to commit `lane.transition` from new code failed three existing `lane-task.test.ts` cases with exactly this error before I removed it.

**What this means for FR-027**: it is unsatisfiable as written. A real residency transition cannot be reported through the type the spec names, because that type is reserved for legacy replay. The two honest options are (a) add a genuinely new, non-legacy event type for real lane transitions — a real catalog change, with its own schema and `kiln check record` negative-suite coverage, which is more than this row's own "no new event type" ground rule allows without a human decision — or (b) accept that real transitions are visible through the already-real, already-committed `lane.acquired`/`lane.swapped`/`lane.released` events plus `kiln.lane`'s document fields, and strike FR-027's specific claim about `lane.transition`.

**What I actually did** (the implementable part, not blocked by this): `grant()` really calls `residency.load()` before granting a lease for a model not yet resident (a real HTTP call, proven live against Ollama); `release()` really calls `residency.unload()` unless the model is pinned (FR-024, also proven live). Neither emits `lane.transition`. The `kiln.lane` document gained `pin: string | null` and `budgetBytes: number | null` (plain document fields, not events — the "no new event type or field" ground rule is about the event catalog specifically, per `data-model.md` §8's own heading; `kiln.lane`'s document shape has grown with every row since r13 without a schema change each time). Proof that a real transition happened is the test suite's own spy on the (fake, for unit tests; real, for the one live test) `Residency` object's `load`/`unload` calls — not a new committed event.

**A trade-off this surfaced, worth flagging though not blocking**: `release()` unloads the model on every release unless pinned (tasks.md's own instruction, contracts/residency-manager.md's own wording). This means two consecutive units needing the *same* model, with nothing pinning it, pay a real unload-then-reload between them — the opposite of what model affinity (constitution IV, LANE-2) tries to achieve. It does **not** miscount as a swap (`doc.resident`'s value never changes across the cycle, confirmed by test), so FR-023's guarantee holds; it is purely an efficiency question for a later row (the host scheduler, LANE-4/r25, or a smarter "keep warm between affinity-adjacent units" policy) to improve, not something this row's acceptance criteria ask it to optimize.

**Decision needed before this row closes** (recommend surfacing to the user/Roadmap-adjacent review, not resolving unilaterally): what to do about FR-027 and the `lane.transition` sentence in `research.md`/`data-model.md`. I did not amend `spec.md` myself — that is a spec-level call, not an implementation judgment call.

## Found during orchestrator review of T023-T028: the interruption notice fires on every resume with a prior tool call, not only after a real kill

**Confirmed, not assumed**: `runTurn` is fully stateless — each call rebuilds the whole message history from `checkpoint.toolCalls` alone (research R4) and has no signal distinguishing "this process just restarted after a kill" from "this is simply the next scheduled round of an ongoing, uninterrupted conversation." `conversation.test.ts`'s own second-resume test (`"ALREADY EXECUTED"` assertion) proves the notice appears on *every* resume with a non-empty log — the test suite codifies this as correct, it is not an oversight that slipped past testing.

**What this means for spec.md**: User Story 2's acceptance scenario 3, as originally written ("a step that never called a non-replay-safe tool... behaves exactly as an uninterrupted step would — no interruption notice is needed or given"), does not hold for any multi-round step past its first round, kill or no kill. **Corrected in spec.md** (not a judgment call left open — SC-002 already specified the built behavior exactly: "100% of resumed steps that had a prior tool call receive a structured interruption notice"), so the two were already in tension and this resolves it in SC-002's favour rather than the narrower scenario's.

**Why this is the safer choice, not a shortcut**: the replay-discipline guarantee (never re-issue a logged write) does not depend on the notice appearing only after a real kill — it depends only on the model never being asked to decide about an already-logged call again, which `runTurn`'s `pending`/`toolCalls` bookkeeping already guarantees regardless of the notice. Always showing the notice when there is something to show is strictly safer than guessing whether this round "counts" as a real interruption and getting it wrong. The cost is purely one of prompt quality: a model doing ordinary multi-round tool use is told "you were interrupted" on every round after the first, which is not literally true and could read oddly to it — worth a later row's attention (e.g. once there is a real signal for "this process actually restarted") but not a correctness or safety defect.

## T032/T033 — readiness lives in `conversation.ts`, not `residency.ts`'s `load()`

T033's own wording sketched `load()` re-running `probe()`. Built differently, deliberately: `WorkersConfig` gained an optional `probe?: (model: string) => Promise<Readiness>` (production: `(model) => residency.probe(model)`), called fresh inside `callModel`, once per `runTurn` invocation — never cached, never passed through `load()`. Two reasons: (1) `load()` operates on a bare model name with no idea which *role* is asking or what that role's tools require, so a capability check belongs with the caller that knows the requirement (`conversation.ts`'s `toolDecls.length > 0` check), not with residency; (2) `load()`'s existing `ollamaModelSize` lookup already independently re-verifies the model is still installed on every call (it throws if not found in `/api/tags`), so folding `probe()` into `load()` too would re-probe capabilities on every *lease* acquisition even when nothing about the role's needs changed between two units sharing a model — wasteful for no added safety, since the real guarantee (FR-042: never trust a cached probe) only needs the check to run fresh at the point something is ACTUALLY requested, which `callModel` already is. `requireCapability(model, need, readiness)` itself is the exact pure signature `contracts/worker-conversation.md` already specified — only where the probing that feeds it happens moved.

`CapabilityRefused` reuses `conversation.ts`'s existing injection-seam pattern (`complete`, `timeoutMsOverride`): `probe` is optional, defaulting to skipping the check entirely when absent (most existing unit tests, which don't exercise this path and shouldn't need to configure it). T037's CLI wiring must supply a real `probe` for the guarantee to hold in a production run — flagged here so it isn't missed, the same way T019's own port-wiring gap was flagged ahead of being hit.

## Found starting T038 — a bigger gap than T037 alone: the walk engine never threads a real role into any unit it creates

**Confirmed, not assumed.** T037's text (and `research.md`/`data-model.md`) only ever describe wiring a lane and a `workers` port into the CLI's `ownerCommand`. That is necessary but not sufficient: `durable/src/walk/walk.ts`'s `work()` phase — the function that actually creates each gate's units from `unitRoles()`'s `todo` list (`"author"`/`"check"`/`"judge"`, or a fix-round's `"workers"`/`"judge"`) — builds every unit as `{label, steps: 1, ...(stepMs ? {stepMs} : {})}` and nothing else. There is no field anywhere that lets a flow **walk** (as opposed to the flat `script: UnitSpec[]` row shape T019 built real roles into) bind a `todo` entry to a real role and model. Without this, SC-001 ("a feature walks every applicable gate with every worker and judge step a real conversation") is unreachable through the walk engine at all, no matter how well T037's CLI wiring works — a real `kiln owner` with a real lane and real workers would still run a full flow walk entirely scripted, because `work()` never asks for anything real.

**Fixed, additively, the same way T037 itself was handled when it was found**: `WalkInput.script` (already the home of this row's other "test knob" fields, `sameContent`/`stepMs`) grows an optional `real: { roles: Record<string, {role, model}>; workspace: string }` (`durable/src/walk/input.ts`, validated the same way every other `script` field is). `walk.ts`'s `work()` looks up the current `todo` entry's name in `real.roles`; when found, the created unit also carries `role`, `model`, `workspace`, `needsLane: true` — the exact shape T019 already proved `kiln.unit` handles. When `real` is absent (every walk before this field existed, and every walk that doesn't set it), `work()` is byte-identical to before: confirmed by re-running the full existing walk suite (78/78, unchanged) after the change. PROVISIONAL, same status as the roster itself (`#workers/roster.ts`) — r18's director replaces this wholesale with a real per-feature role assignment once it exists; until then it is the only way a *walk* (not a flat script) reaches a real conversation.

**Why this belongs in this row's own discretion rather than a stop-and-report**: it is the same kind of additive, minimal, pattern-matching fix T037 itself already was (adding a provisional mapping, not redesigning anything proven) — the walk's existing scripted behavior is untouched for every input that doesn't opt in, exactly the bar T037's own fix was held to.

**Superseded — the above guess was wrong, and the real cause was a genuine bug, not real generation cost.** Progress logging plus per-call instrumentation inside `grant()` (added, used, then removed) showed the walk was not merely slow: it sat for the *entire* 15 (then 40) minute budget with Ollama completely idle (`/api/ps` empty, 0% CPU) immediately after the second gate's units finished — no request in flight at all. A minimal repro (`residency.load()` → `unload()` → `load()` again, directly, no walk) completed in 1.7s with no issue, ruling out `residency.ts` itself. The real cause, found by instrumenting `grant()` directly: **`lane-task.ts`'s `release()` set `holder = null` *before* awaiting `residency.unload()`.** `acquire()` calls `pump()` itself the instant a new waiter is queued — it does not wait to be told the lane is free — so with `holder` already cleared, the *next* unit's `grant()` (its own `reconcile()` + `load()`) could run concurrently with the *current* unit's still-in-flight `unload()`, racing on `residency`'s internal `own` bookkeeping map for the same model. Whichever of the two `own.set`/`own.delete` calls resolved last silently won; when `unload()`'s `own.delete()` won after a next unit's `own.set()` had already succeeded, that next unit was left with no record of a model it had genuinely, successfully loaded — and its own next `reconcile()` call (or the gate after it) then reported Ollama's real resident model as a broken guarantee nobody asked for, throwing `LaneError` from `grant()` repeatedly (the retry mechanics of the pinned task runtime kept re-entering `work()`, re-hitting the identical race, forever — a real infinite retry loop, not a single failure).

**Fix**: moved `holder = null` to *after* the `residency.unload()` call resolves (`lane-task.ts`), so a release's real HTTP unload and the next acquire's real HTTP load can never overlap for the same lane — serialized, at the cost of one release's latency, never a correctness compromise. Confirmed: the exact transition that previously hung for the *entire* 15/40-minute budget (`2a-experience` → `3-spec`) now completes in under 20 seconds, and the full 9-gate small-interface walk with real roles reaches Merge in ~210s (SC-001, `real-worker-walk.test.ts`). `npm run proof` (132/132) and the `lane`/`durable` unit suites were re-run after the fix and show no regression — the serialization only affects the narrow window between a release and the next acquire, which every existing test's timing tolerance already accommodates.

## T039 — a real model occasionally hallucinates an undeclared tool name; correctly refused, but worth a prompt fix, not a design change

**Found live, not invented**: the first run of the kill-mid-generation proof failed — not from the kill, from the model itself. ## T039, second real finding — a restarted process's own residency bookkeeping is always empty, and keep_alive:-1 means Ollama never forgot: every real kill-and-restart tripped a false broken-guarantee

**Confirmed by actually killing the owner and restarting it**, not reasoned about in the abstract. After the prompt fix above, the retry hit a DIFFERENT failure at the SAME point: `grant()`'s `reconcile()` (T029) refused the resumed unit's re-acquire with "Ollama reports 'gemma4:12b' resident, but the residency manager never asked for it" — except this time Ollama was telling the truth about something KILN itself put there: the FIRST (now-dead) owner process's `residency.load()` had set `keep_alive:-1` before it was SIGKILLed, so the model never expired; the RESTARTED owner process's `createResidency()` call starts with a brand-new, empty `own` map (an in-memory bookkeeping structure, by design — nothing about it is meant to be durable on its own). From the new process's own, honest point of view, it genuinely never asked for that model; from the system's point of view, nothing bypassed anything. **This is not a rare coincidence — it is the deterministic, every-time outcome of killing an owner while any real unit holds a lease**, which means the row's own acceptance line ("a crash mid-generation resumes without double-charging a tool") was unreachable for any real-role unit the moment the kill happened to land while a lease was held, for exactly the scenario T039 exists to prove.

**Fix**: `Residency.reconcile()` gained an optional `expected` parameter — the model the caller (`grant()`, which already has it as `w.opts.model`) is about to request. When Ollama's resident set is otherwise explained and the one unexplained model is exactly `expected`, `reconcile()` **adopts** it (`own.set(...)`, re-deriving its size) rather than reporting a broken guarantee — proven not to be a silent skip by a test that then calls `unload()` on the adopted model and checks it is genuinely tracked (`unloaded: true`, not the no-op `unload()` already gives an untracked model). Anything resident that is *not* the expected model is still reported exactly as before (a second new test covers this explicitly, so the fix narrows the check, it does not disable it).

**The trade-off, stated plainly rather than buried**: this narrows OBS-5's detection for one specific case — if something *other* than KILN happened to load the *exact same model name* KILN's own next acquire is about to request anyway, it is now silently adopted rather than flagged. Weighed against the alternative — the row's core crash-resume guarantee being unreachable for every real-role lease-holding kill — this is the right side to give way on: adopting a model that ends up exactly where KILN's own bookkeeping would have put it anyway changes no resident model, no budget accounting, and no safety property; it only changes whether a legitimate restart is mistaken for a bypass. A later row building real multi-host or multi-operator scenarios, where "someone else loading the identical model name at the identical moment" stops being a restart artifact and starts being a real possibility, should revisit this — not this row's to solve.

## Found by the orchestrator, outside any single task: `tests/walk/drive.ts`'s `kiln()` helper had no process timeout at all

While the implementing agent was mid-debug on the T038/T039 hangs above, its own test run sat for over 7 hours wall-clock on a since-fixed race — but the deeper, separate gap that let it sit that long rather than fail loudly is in the test tooling itself, not the row's product code. `tests/walk/drive.ts`'s `kiln()` (the CLI-subprocess spawner `drive()` uses internally) had no `setTimeout`/SIGKILL at all, unlike its near-identical twin in `packages/cli/tests/support/kiln.ts`. `drive()`'s own `patienceMs` only bounds the *retry* loop for exit codes 3/4 (owner-away); it does nothing if a single spawned process simply never exits. Every caller before r16 only ever drove scripted, millisecond-scale work, so this was never reachable in practice — a real generation (or a real bug in new integration code) is the first thing slow enough to expose it.

**Fixed**: `kiln()` now takes an optional `timeoutMs` (default 120s) and SIGKILLs the child if it fires; `DriveOptions` grew a matching optional `subprocessTimeoutMs`, threaded through both of `drive()`'s own call sites, defaulting to the same 120s when unset. Confirmed non-breaking: all three existing callers (`feature-cli.test.ts`, `feature-cli.proof.test.ts`, `owner-wiring.test.ts`) re-run clean (9/9 pass) after the change. This is defensive test-infrastructure hardening, not a product-code fix — but a real one: without it, any future hang (in this row's own machinery or a later row's) would again silently consume however many hours rather than failing fast and loud.

## T047 — code review (manual, this fork has no `/code-review` skill access): one real finding

**Confirmed by reading the code, not guessed**: `conversation.ts`'s `callModel` calls `config.probe(input.model)` fresh on *every* call — and `callModel` runs once per conversation round (`runTurn`'s "ask the model for a fresh round" branch), not once per model-load. `residency.ts`'s `probe()` itself makes **three separate real generations** against Ollama (`probeToolCalling`, `probeStreaming`, `probeUsage`) plus one cheap metadata call (`ollamaContextWindow`, via `/api/show`, not a generation). So a single step pays up to 3 extra real generations *before* its own real answer, on **every round** — up to `MAX_TOOL_ROUNDS` (4) × 4 real calls = up to 16 real generations for one step that hits the round cap, where exactly 1 would do the actual work.

**Correctness is not affected — FR-042/SC-005 are still met, arguably over-satisfied** (a capability that disappears is still caught, just far more often than the one re-check-at-point-of-use the spec actually asks for). **Not fixed here**: this is a genuine design trade-off between "re-probe aggressively, pay the cost every round" (built) and "probe once per model-becomes-resident, cache until unload" (cheaper, still satisfies FR-042's literal wording — "re-checked at the point a model is actually requested to become resident" reads as a *load-time* check, not a *per-round* one). Redesigning the caching boundary during Polish, under time pressure, risks introducing a new bug for a performance question that doesn't change any guarantee — recorded as an open item (implementation-report.md §7) for a deliberate decision rather than rushed here. It is also a material, confirmed contributor to this row's own live-walk timings (~185–215s) and to today's load-driven test flakiness (§8 of the same report) — probing alone, at ~3 real generations per round, plausibly accounts for a large fraction of each gate's wall-clock time.
