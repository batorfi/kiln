## 2026-10-27 — US1/US2/US3 (what the first walks and the first kills found)

* **`openGate` waited 3 s per gate when called from a task step.** The r13 bounded wait ("opened means the gate can take a move") polls for the decision step's slot; but a gate is two library tasks that the scheduler cannot start while the *opening task's step is still running*. So every other gate of a walk stalled for the full 3000 ms (measured: 18 s for a 12-gate walk against 0.2 s in-process). Fix: `openGate(s, key, spec, { awaitRegistered: false })` for the walk (r13's default is unchanged), and `readWalk` shows a gate only once its decision step has registered — the registration notifies the watcher — so "open" still means "can take a move" for anyone reading the walk.
* **The first kill test found a real bug.** After a kill at `walk.admit-opened` the restarted owner ran the row's `admit` step *before the owner was ready*; the gate API answered `not-ready`, the row threw, and the task failed for good. A row step that resumes during start-up must wait for readiness: `Services.whenReady` (the factory's `ready` promise) is awaited before the walk touches the gate API. All eleven walk points now pass, each in ~0.55 s.
* **A failing walk must not leak an owner.** The first harness left its child owner alive when a call timed out, so the debugging script itself hung. `runWalk` now cleans up the store (killing every process on it) whenever it throws, and every call has an overall deadline whose failure message says where the store stood (tasks, outcomes, failure messages, entries).
* **"Units are created inside the row's own commit"** differs from the plan's keyed commands (`walk:<f>:unit:…`): creating the unit and parking on it are ONE `run.commit`, exactly-once by construction (all or nothing), needing no key. A simplification, not a loosening.
* **Phase naming.** The plan's `decide` (waiting) and `consume` (acting) are one phase in code: the checkpoint `decide` *is* the state "waiting on the gate task", and the function that runs when the task wakes is the consequence step. `walk.settled-read` fires after the stored record is read; `walk.consume-after-write` inside the commit.

## 2026-10-27/28 — US5–US8, the sabotages, and what the walk taught us

* **Mutation checks, all on a committed tree, each revert verified clean** (`kiln/tests/tools/mutate.ts`; the sabotage files are `mutations-us4/us5/us8.json` beside this notebook).
  * **US4:** delete the Merge-is-last rule · let an empty flow pass · let the glob dialect accept anything — all three caught by the negative suite.
  * **US5:** the withdraw path also writes a move record (caught by the withdrawn-has-no-record test and the withdraw kill test) · a person's move on a withdrawn gate answered `lost-race` instead of `stale` · the walk never applies a recorded feature-level move · a reject to an earlier gate re-crosses nothing · restart returns to the gate it was made at (the FR-025 defect). **The first run caught four of five:** "the walk never applies a recorded move" survived because my test sent the move in the window where the gate was *settled but not yet consumed*, which the `decide` phase handles on its own path; the test now waits until the row is parked on a running step (the real "no gate open" case), and the sabotage is caught.
  * **US8:** a vocabulary changed in `v2.ts` only · in `gate-rail.md` only · a consequence row changed in the contract only — each fails the drift test naming the gate and the field.
* **The weakened walk** (`broken-walk.ts`: a row that opens the next gate without waiting for a person and reads the absence of a move as an approval) is rejected by W1 and by the gate invariants, while the real walk passes the same judge; a kill that never fires fails `proof-point-not-fired`.
* **Round numbering with re-crossing is subtle.** A gate that was never approved before (the one that was rejected, or one not yet reached) has *no* last-approval vector, so its brief names the target but cannot say "what changed since". The first draft of the test assumed it could; the data says otherwise and the brief now says so honestly (`changedSince: []`, `unchanged: false`).
* **A feature-level move can arrive in three windows** — a gate open (withdraw through the decision slot), a step running (recorded, applied at the next wake), and the short window in which a person's move has been committed but the row has not yet consumed it (the gate is ended, the move is recorded, and `decide` applies it AFTER the gate's own outcome — unless that outcome ended the walk). The 60-race test exercises the first and third.
* **`overview.md` §6.2 names `consume` and `decide` as two phases**; in code they are one (see above). The overview is corrected at close-out.
* **Test cost.** The kill tests cost ~0.55 s each once the 3 s `openGate` wait was gone, so the *whole* proof tier (every point × every hit × both walks, the re-crossing walk, the fix-round walk, 300 random kills) is ~3 minutes and the default tier carries a 12-test smoke. The default tier's `npm test` stayed at 185 s (182 s before the row) because the slowest command-line walks live in the proof tier.
