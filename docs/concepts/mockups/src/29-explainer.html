Why the lane refuses to unload a held judge's model

explainerfeature in progress✓ claims checked against code at 7c2e9a1
The short answer. A judge must see the same model from the work it judges to its verdict. Ollama can evict a model under memory pressure, so the lane itself refuses to unload a model while a judge holds it — and the work that needs memory waits instead.

How it works

When a step asks the lane for a different model, the lane first checks whether a judge holds the resident one. If it does, the swap is refused with LaneHeldError, and the model pool keeps the requesting step queued until the judge's verdict releases the hold (Judge hold, Model pool).

In words: a swap request reaches the lane; if a judge holds the resident model the lane refuses and the pool queues the step until the verdict; otherwise the lane unloads and loads as before.

  async swapTo(next: ModelRef): Promise<void> {
    if (next.id === this.resident?.id) return;
    // finding 1: never unload a model a held judge still needs
    if (this.hold && this.hold.model.id === this.resident?.id) {
      throw new LaneHeldError(`lane held by ${this.hold.gate} until its verdict`);
    }
    await this.resident?.unload();
    this.resident = await load(next);

Why not rely on Ollama's keep_alive?

keep_alive asks Ollama to keep a model loaded; it does not guarantee it. On Oct 14 a Design-gate critic lost its model this way and restarted on a cold load (Model eviction mid-judgment, keep_alive is not residency). The check therefore lives in KILN, where it can be enforced — and, as Zsolt's restart note asked, inside the lane, not in its callers.
